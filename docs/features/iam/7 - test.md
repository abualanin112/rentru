# استراتيجية اختبار إدارة الهوية والوصول (IAM Test Strategy)

## فلسفة الاختبار

يعتمد الاختبار على 3 طبقات: وحدوي (Unit) لمنطق الأعمال المعزول، تكاملي (Integration) للتدفقات الكاملة مع قاعدة بيانات حقيقية عبر Testcontainers، وأمني (Security) للتحقق من مقاومة النظام للتلاعب.

---

## 1. اختبارات الوحدات (Unit Tests)

### 1.1 Token Service (`token.service.js`)

| #       | الحالة                                | النتيجة المتوقعة                                                 |
| ------- | ------------------------------------- | ---------------------------------------------------------------- |
| U-TK-01 | إنشاء Access Token بـ payload صالح    | JWT صالح يحتوي على `userId`, `roleId`, `roleVersion`, `branchId` |
| U-TK-02 | إنشاء Refresh Token                   | JWT صالح بعمر 12 ساعة                                            |
| U-TK-03 | التحقق من Access Token صالح           | يُرجع الـ payload بدون أخطاء                                     |
| U-TK-04 | التحقق من Access Token منتهي الصلاحية | يرمي خطأ `TokenExpiredError`                                     |
| U-TK-05 | التحقق من Access Token بتوقيع مزور    | يرمي خطأ `JsonWebTokenError`                                     |
| U-TK-06 | تشفير Refresh Token بـ SHA-256        | الناتج يطابق الهاش المحفوظ في قاعدة البيانات                     |

### 1.2 Authorization Middleware (`authorize.middleware.js`)

| #       | الحالة                                                            | النتيجة المتوقعة                  |
| ------- | ----------------------------------------------------------------- | --------------------------------- |
| U-AZ-01 | مستخدم يمتلك الصلاحية المطلوبة بالضبط                             | `next()` يُستدعى                  |
| U-AZ-02 | مستخدم لا يمتلك الصلاحية                                          | `403 Forbidden`                   |
| U-AZ-03 | Super Admin بصلاحية `*:*:*`                                       | `next()` يُستدعى لأي مسار         |
| U-AZ-04 | `roleVersion` في التوكن ≠ الإصدار في الـ DB                       | `401 Unauthorized`                |
| U-AZ-05 | Scope Hierarchy: مستخدم يمتلك `:any` يحاول الوصول لمسار `:own`    | `next()` يُستدعى (التسلسل الهرمي) |
| U-AZ-06 | Scope Hierarchy: مستخدم يمتلك `:own` يحاول الوصول لمسار `:branch` | `403 Forbidden`                   |

### 1.3 Session Service (`session.service.js`)

| #       | الحالة                                                           | النتيجة المتوقعة                                |
| ------- | ---------------------------------------------------------------- | ----------------------------------------------- |
| U-SS-01 | إنشاء جلسة جديدة لمستخدم بدون جلسة سابقة                         | سجل جلسة واحد في الـ DB                         |
| U-SS-02 | إنشاء جلسة جديدة لمستخدم لديه جلسة موجودة (Strict Single Device) | Upsert يستبدل الجلسة القديمة، يبقى سجل واحد فقط |
| U-SS-03 | حذف جلسة عند تسجيل الخروج                                        | الجلسة تُحذف من الـ DB                          |
| U-SS-04 | محاولة حذف جلسة غير موجودة (Idempotent Logout)                   | لا يحدث خطأ، يُرجع `200 OK`                     |

### 1.4 Invitation Service (`invitation.service.js`)

> **ملاحظة فنية (Queue Mocking):** يجب استخدام `vitest.mock()` لإسكات محرك الإيميلات (SMTP) أو الـ Worker أثناء اختبارات الوحدة (Unit Tests)، وخاصة في الحالة `U-IN-01`، وإلا ستفشل اختبارات الـ CI/CD بسبب محاولة الاتصال بخادم بريد حقيقي.

| #       | الحالة                                      | النتيجة المتوقعة                            |
| ------- | ------------------------------------------- | ------------------------------------------- |
| U-IN-01 | إنشاء دعوة بمدخلات صالحة                    | سجل `Invitation` بحالة `PENDING`            |
| U-IN-02 | إنشاء دعوة لبريد موجود مسبقاً كمستخدم نشط   | `409 Conflict`                              |
| U-IN-03 | إنشاء دعوة لبريد لديه دعوة `PENDING` مسبقاً | `409 Conflict`                              |
| U-IN-04 | قبول دعوة صالحة                             | إنشاء `User` + تحديث الدعوة إلى `COMPLETED` |
| U-IN-05 | قبول دعوة منتهية الصلاحية                   | `403 Forbidden`                             |
| U-IN-06 | إبطال دعوة (Revoke)                         | تحديث الحالة إلى `REVOKED`                  |

### 1.5 User Service (`user.service.js`)

| #       | الحالة                       | النتيجة المتوقعة                                                  |
| ------- | ---------------------------- | ----------------------------------------------------------------- |
| U-US-01 | أرشفة موظف بدون مهام مفتوحة  | `deletedAt` يُعيّن + `isActive: false` + جلسة تُحذف (Transaction) |
| U-US-02 | أرشفة موظف لديه مهام مفتوحة  | `400 Bad Request` مع رسالة توضيحية                                |
| U-US-03 | إيقاف مؤقت (Kill-Switch)     | `isActive: false` + جلسة تُحذف (Transaction)                      |
| U-US-04 | استعادة موظف مؤرشف (Restore) | `deletedAt: null` + `isActive: true`                              |
| U-US-05 | محاولة المدير إيقاف نفسه     | `403 Forbidden`                                                   |
| U-US-06 | محاولة المدير أرشفة نفسه     | `403 Forbidden`                                                   |

## 2. اختبارات التكامل (Integration Tests — Testcontainers + Supertest)

### 2.1 تدفق المصادقة الكامل (Auth Flow)

| #       | التدفق                                             | النتيجة المتوقعة                                           |
| ------- | -------------------------------------------------- | ---------------------------------------------------------- |
| I-AU-01 | Google SSO Login → Session Created → Tokens Issued | `200 OK` + Access Token في الجسم + Refresh Token في Cookie |
| I-AU-02 | Login بموظف موقوف (`isActive: false`)              | `403 Forbidden`                                            |
| I-AU-03 | Login بموظف مؤرشف (`deletedAt ≠ null`)             | `403 Forbidden`                                            |
| I-AU-04 | Login من جهاز جديد → الجلسة القديمة تُحذف          | سجل واحد فقط في جدول `Session`                             |
| I-AU-05 | Login ببريد غير مسجل وبدون دعوة                    | `403 Forbidden`                                            |

### 2.2 تدفق تدوير الرموز (Token Rotation)

| #       | التدفق                                                                                            | النتيجة المتوقعة                                                                                                |
| ------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| I-TR-01 | Refresh بـ Refresh Token صالح                                                                     | `200 OK` + رموز جديدة + تحديث الهاش في الـ DB                                                                   |
| I-TR-02 | Refresh بـ Refresh Token مستخدم مسبقاً (Reuse بعد Grace Period)                                   | `401 Unauthorized` + حذف الجلسة + حدث تدقيق                                                                     |
| I-TR-03 | Refresh بعد إبطال الجلسة إدارياً                                                                  | `401 Unauthorized`                                                                                              |
| I-TR-04 | Refresh بعد تسجيل الخروج                                                                          | `401 Unauthorized`                                                                                              |
| I-TR-05 | إرسال طلبين متزامنين (Parallel Requests) لـ `/refresh` بنفس الـ Refresh Token في غضون ثانية واحدة | الطلب الأول يُرجع `200 OK`. الطلب الثاني يُسمح به أيضاً (Grace period) أو يُرجع نفس النتيجة لمنع الإبطال الكاذب |

### 2.3 تدفق التسجيل الأول (Onboarding)

| #       | التدفق                                      | النتيجة المتوقعة                             |
| ------- | ------------------------------------------- | -------------------------------------------- |
| I-OB-01 | الدعوة → قبول عبر Google SSO → إنشاء مستخدم | `User` جديد + `Session` + الدعوة `COMPLETED` |
| I-OB-02 | محاولة قبول دعوة ببريد مختلف عن المدعو      | `403 Forbidden`                              |
| I-OB-03 | محاولة قبول دعوة مُبطلة (REVOKED)           | `403 Forbidden`                              |

### 2.4 تدفق RBAC والعزل الجغرافي (Authorization + Branch Isolation)

| #       | التدفق                                        | النتيجة المتوقعة                            |
| ------- | --------------------------------------------- | ------------------------------------------- |
| I-RB-01 | موظف فرع A يحاول قراءة بيانات فرع B           | القائمة فارغة (Silent Guardian يحقن الفلتر) |
| I-RB-02 | Super Admin يقرأ بيانات جميع الفروع           | يرى كل البيانات                             |
| I-RB-03 | تحديث صلاحيات دور → `version` يزداد           | الطلب التالي بالتوكن القديم يُرفض `401`     |
| I-RB-04 | محاولة تصعيد الصلاحيات (Privilege Escalation) | `403 Forbidden`                             |

### 2.5 تدفق سجل التدقيق (Audit Logs Flow)

| #       | التدفق                                   | النتيجة المتوقعة                                                                                                    |
| ------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| I-AL-01 | تعديل صلاحيات دور وظيفي (`PUT /roles`)   | إنشاء سجل `AuditLog` يحمل `actorId` الصحيح، ويحتوي على الصلاحيات القديمة والجديدة في حقول `oldValues` و `newValues` |
| I-AL-02 | تنفيذ الإيقاف الفوري (Kill-Switch) لموظف | إنشاء سجل التدقيق يوثق حدث `user.suspended` مع تسجيل الـ `ipAddress`                                                |

### 2.6 تدفق زرع المؤسس (Super Admin Bootstrap - ADR-001)

| #       | التدفق                                           | النتيجة المتوقعة                                                    |
| ------- | ------------------------------------------------ | ------------------------------------------------------------------- |
| I-BS-01 | تشغيل `seed` مع وجود المتغير `SUPER_ADMIN_EMAIL` | إنشاء دور `Super Admin` (`level: 100`) + مستخدم بـ `googleId: null` |
| I-BS-02 | محاولة تشغيل `seed` بدون المتغير                 | رمي خطأ وإيقاف العملية (Fatal Error) لمنع نشر النظام بدون مدير      |

## 3. اختبارات الأمان (Security Tests)

| #    | السيناريو                                                            | النتيجة المتوقعة                         |
| ---- | -------------------------------------------------------------------- | ---------------------------------------- |
| S-01 | إرسال طلب بدون `Authorization` header                                | `401 Unauthorized`                       |
| S-02 | إرسال JWT مزور (توقيع خاطئ)                                          | `401 Unauthorized`                       |
| S-03 | إرسال JWT صالح لمستخدم موقوف                                         | `403 Forbidden`                          |
| S-04 | إرسال `deviceId` فارغ في `/auth/google`                              | `400 Bad Request` (Zod Validation)       |
| S-05 | محاولة الوصول لـ API بدون صلاحية                                     | `403 Forbidden`                          |
| S-06 | Rate Limiting: إغراق `/auth/refresh`                                 | `429 Too Many Requests` بعد الحد المسموح |
| S-07 | استجابة API لا تحتوي على `googleId` أو `refreshTokenHash`            | التحقق من عدم تسريب البيانات الحساسة     |
| S-08 | Refresh Token Cookie لا يحمل `HttpOnly`, `Secure`, `SameSite=Strict` | فشل الاختبار إذا غاب أي حقل حماية        |
