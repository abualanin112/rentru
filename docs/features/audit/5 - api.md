# توثيق واجهة Audit Logging البرمجية (API Documentation)

## مسارات واجهة برمجة التطبيقات (API Endpoints)

تم استثناء وحدة التدقيق من كونها مخفية، وتوفير مسار آمن للقراءة فقط لخدمة المحاسبين والمديرين.

### مسار استعراض السجلات (List Audit Logs)

- **المسار:** `GET /api/v1/audit`
- **الغرض:** استرجاع سجلات التدقيق مع دعم كامل للفلترة والترحيل (Pagination).
- **الصلاحيات المطلوبة (RBAC):** - `read:audit:any`: للمدير العام (Super Admin) لرؤية كل حركات النظام.

      - `read:audit:branch`: لمدير الفرع أو المحاسب لرؤية الحركات التي تمت داخل نطاق فرعه فقط.

  -لابد من اضافة وتعديل ذلك في قائمة الصلاحيات ان لم تكن كذلك. كهيستوري في ال ui.

#### معلمات البحث والفلترة (Query Parameters):

يجب أن يدعم المسار الفلاتر والمعلمات التالية لتمكين الفرونت إند من بناء شاشات تتبع قوية:

- `entityType`: فلترة بنوع الكيان (مثال: `Contract`, `Invoice`, `User`).
- `entityId`: لعرض "القصة التاريخية" لكيان محدد (مثال: تمرير ID عقد معين لمعرفة من عدله).
- `actorId`: لمعرفة كل الحركات التي قام بها موظف معين.
- `action`: فلترة بنوع الإجراء (`CREATE`, `UPDATE`, `DELETE`).
- `startDate` & `endDate`: فلترة بنطاق زمني.
- `limit`: عدد السجلات المطلوب جلبها في الصفحة الواحدة (قيمة عددية بين 1 و 100، القيمة الافتراضية هي 50).
- `cursor`: مؤشر تصفح مشفر بصيغة Base64 يمثل كائن JSON يحتوي على الحقلين `createdAt` و `id` لآخر سجل تم استرجاعه (على سبيل المثال: `eyJjcmVhdGVkQXQiOiIyMDI2LTA2LTEy...", "id": "..."}`).

#### التحقق من صحة المؤشر (Cursor Validation & Errors):

يتم إخضاع المعلمة `cursor` لفحص صارم عبر مخطط التحقق `genericCursorSchema` لضمان:

1. فك تشفير النص المشفر بنجاح من صيغة Base64 إلى صيغة JSON صالحة.
2. احتواء الكائن الناتج على المعرف الفريد `id` بصيغة `UUIDv4`.
3. وجود حقل ترتيب زمني إضافي (مثل `createdAt`).

في حال تمرير مؤشر غير صالح أو تالف، يتم رفض الطلب فوراً وتوليد استجابة خطأ `400 Bad Request` بالصيغة القياسية للتحقق دون التسبب في خطأ داخلي في الخادم `500 Internal Server Error`.

#### قيود الأمان (Security Constraints):

- **حظر التعديل (No Mutation):** يُمنع منعاً باتاً برمجة أي مسارات من نوع `POST`، `PUT`، أو `DELETE` في متحكم التدقيق (Audit Controller). جدول التدقيق هو للكتابة الخلفية (عبر الـ Service) وللقراءة الأمامية (عبر الـ API) فقط.
- **إخفاء الـ Metadata:** لا يتم إرجاع حقل `metadata` بالكامل في قائمة الاستعراض السريع لتخفيف حجم الاستجابة (Payload Size)، بل يُكتفى بعرضه عند طلب سجل محدد.

## واجهة التكامل بين الوحدات (Inter-Module Interface)

تتفاعل الوحدات الأخرى مع نظام التدقيق حصريًا من خلال الخدمة المصدّرة `auditService`:

JavaScript

```
import { auditService } from '../../audit/index.js';

// تنفيذ قياسي
await auditService.logEvent({
  event: 'notes.created',
  targetType: 'Note',
  targetId: note.id,
  action: 'CREATE',
  metadata: { title: note.title },
});

// تنفيذ داخل معاملة (Transaction)
await auditService.logEvent(
  {
    event: 'users.deleted',
    targetType: 'User',
    targetId: user.id,
    action: 'DELETE',
  },
  prismaTransactionClient,
);
```

## نمط الاستخدام (Usage Pattern)

- تستدعي الوحدات المختلفة `auditService.logEvent()` لتسجيل أحداث التدقيق.
- **في السيناريوهات العادية:** تُمرَّر بيانات الحدث فقط.
- **في السيناريوهات المعاملاتية (Transactional Scenarios):** يمكن تمرير عميل Prisma الخاص بالمعاملة (`prismaTransactionClient`) كمعامل ثانٍ لضمان تسجيل الحدث داخل نفس المعاملة.
- تتولى خدمة التدقيق تلقائيًا استخراج معلومات السياق (`reqId` و `actorId`) وتنقية البيانات الحساسة قبل حفظ السجل.
- لا تحتاج الوحدات المستهلكة للخدمة إلى التعامل مباشرة مع جدول `AuditLog` أو منطق التنقية والحفظ الداخلي.
