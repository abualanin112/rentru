# تدفق العمليات (Flows)

## 1. مسار تسجيل التدقيق المعاملاتي (Transactional Audit Flow)

1. يستقبل الـ `Controller` الطلب.
2. يبدأ الـ `Service` معاملة (Prisma Transaction).
3. يتم التعديل على الكيان الأساسي (مثال: حذف `Note`).
4. يُستدعى `audit.service.logEvent` مع تمرير كائن الـ `tx`.
5. يستخرج الـ `logEvent` الـ `actorId` و `reqId` من `AsyncLocalStorage`.
6. يتم تطهير الـ `metadata` (Sanitization).
7. تُحفظ التغييرات وحدث التدقيق في نفس المعاملة بنجاح أو تفشل بالكامل.

## 2. مسار التسجيل غير المتزامن (Fire-and-Forget Flow)

للأحداث غير الحرجة التي لا تقع ضمن معاملة متزامنة مع تعديل كيانات رئيسية.

1. يُستدعى `audit.service.logEvent` بدون تمرير معاملة `tx`.
2. **هام جدًا:** يجب أن يُحاط الاستدعاء بـ `try/catch` أو أن يتم تغليفه بـ `catchAsync` مخصص لضمان عدم حدوث (Unhandled Promise Rejection) الذي قد يوقف النظام.

## 3. مسار استرجاع لوحة التحكم (Admin Dashboard Fetch Flow)

1. يستقبل `AuditController` طلب `GET /v1/audit`.
2. يتم التحقق من الصلاحيات عبر الاستعلام المباشر في قاعدة البيانات (Direct DB RBAC).
3. يستخدم `AuditRepository` استعلام Prisma مدعوم بـ Cursor Pagination والفهارس المركبة.
4. **تخطي الحارس الصامت (Guardian Bypass):** الاستعلام يطبق آلية تخطي (Bypass) لامتداد الحذف المنطقي لاسترجاع بيانات الـ `User` المرتبط بـ `actorId` حتى لو كان الموظف محذوفاً منطقياً. إرجاع السجلات مدمجة ببيانات منفذ الحدث لتسهيل القراءة.

## 4. مسار الإرسال الخارجي (Event Forwarding Flow)

1. يعمل العامل المجدول عبر `node-cron` بشكل دوري داخل نفس عملية التطبيق (In-Process Worker).
2. يحصل على قفل `pg_try_advisory_lock` عبر PostgreSQL لمنع التكرار بين الخوادم المتعددة.
3. يقرأ السجلات التي لم يتم إرسالها للأنظمة الخارجية (تطبيق Outbox Pattern مباشرة على جدول `AuditLog`).
4. يرسل البيانات للأنظمة الخارجية كـ (Datadog/Kinesis).
5. يحدث حالة السجلات في الداتا بيز بنجاح الإرسال (مثلاً تعيين `forwardedAt`).
6. يحرر القفل الاستشاري.
