# ملاحظات سجل التدقيق (Audit Logging Notes)

## المعمارية المنجزة للنمو والتحجيم (Implemented Scalability Architecture)

- **محرك التصفح بالمؤشرات الموحد (Universal Cursor Pagination Engine):** تم بالكامل تنفيذ وتفعيل التصفح المعتمد على المؤشرات الثنائية المحددة `(createdAt, id)` عبر الأداة المشتركة `CursorPaginate.js`. يحل هذا الحل المعماري مشكلة نمو جدول `AuditLog` ويمنع تكرار أو تخطي السجلات أثناء الإدراج المتزامن المكثف.
- **الفهارس المركبة الإلزامية (Mandatory Composite Indexes):** لضمان أداء استعلامات التصفح بتعقيد زمني قدره $O(1)$ ومنع تكوين عقد فرز في الذاكرة (in-memory sorting)، تم فرض وتعريف فهرس مركب على مستوى قاعدة البيانات لنموذج `AuditLog` يغطي حقل الترتيب والمعرف الفريد بترتيب تنازلي متطابق: `@@index([createdAt(sort: Desc), id(sort: Desc)])`.

## الدين التقني (Technical Debt)

- **أرشفة السجلات (Log Archival):** حاليًا يستمر جدول `AuditLog` بالنمو دون حدود. لذلك نحتاج إلى مهمة مجدولة (Cron Job) أو عامل خلفي (Background Worker) لنقل السجلات التي يزيد عمرها عن 90 يومًا إلى صيغة أرشفة مخصصة للتخزين البارد (Cold Storage)، مثل ملفات CSV مخزنة في كلاود فلير، ثم حذفها من قاعدة بيانات PostgreSQL النشطة.

## الافتراضات (Assumptions)

- **الحفظ المتزامن (Synchronous Persistence):** نفترض أن عملية إدراج السجلات داخل جدول `AuditLog` لا تشكل عنق زجاجة (Bottleneck) مؤثرًا على زمن استجابة طلبات HTTP الرئيسية. وإذا أصبحت هذه العملية مؤثرة على الأداء مستقبلًا، فقد نحتاج إلى معالجة أحداث التدقيق بشكل غير متزامن (Asynchronously) — مثل استخدام نمط Fire-and-Forget Promises — بدلاً من كتابتها مباشرة إلى PostgreSQL أثناء دورة حياة الطلب (HTTP Lifecycle). ومع ذلك، فإن هذا النهج سيؤدي إلى كسر متطلب الذرية المعاملاتية (Transactional Atomicity) الخاص بعمليات التعديل، حيث لن يعود بالإمكان ضمان اعتماد (Commit) أو التراجع (Rollback) عن بيانات الأعمال وسجل التدقيق معًا ضمن نفس المعاملة.

### ملاحظات إضافية مقترحة (Suggested Additional Notes)

#### 1. سلامة قاعدة البيانات (Database-Level Integrity)

- **المشكلة:** تطبيقنا يمنع تعديل أو حذف سجلات التدقيق عبر الكود (لا توجد مسارات `DELETE` أو `UPDATE`). لكن ماذا لو دخل شخص مباشرة إلى قاعدة البيانات عبر (DB Client) وقام بحذف صف؟
- **الحل المعماري (مستقبلي):** كدين تقني، يجب إضافة (PostgreSQL Trigger) على مستوى محرك قاعدة البيانات نفسه، يرفض أي استعلام `UPDATE` أو `DELETE` يُنفذ على جدول `AuditLog`، لضمان أن السجل غير قابل للعبث (Tamper-Proof) حتى من قِبل مديري قواعد البيانات (DBAs).

#### 2. توحيد المنطقة الزمنية (Timezone Consistency)

- **المشكلة:** النظام يتعامل مع حجوزات وعمليات مالية دقيقة بوقت حدوثها.
- **القرار المعماري:** يجب أن يُحفظ الحقل `createdAt` في قاعدة البيانات بتوقيت (UTC) دائماً. ولكن عند استعراض السجلات عبر مسار واجهة برمجة التطبيقات `GET /api/v1/audit`، يجب أن يقوم الفرونت إند بتحويل هذا التوقيت إلى المنطقة الزمنية المحلية (مثلاً بتوقيت القاهرة)، لكي لا يحدث ارتباك للمحاسب عند مراجعة توقيت إصدار أو تعديل العقود.

#### 3. تجربة المستخدم التشغيلية (Operational UX)

- **المشكلة:** جدول التدقيق يخزن التغييرات ككائنات JSON معقدة في حقل `metadata` (مثل: `{"status": "PAID"}`). المحاسب أو مدير الفرع لن يفهم هذه الصيغة التقنية بسهولة.
- **القرار المعماري:** مسار الـ API الخاص بالتدقيق لا يجب أن يرمي الـ JSON الخام في وجه المستخدم. يجب بناء طبقة (Serializer) بسيطة في Express.js تترجم هذه التغييرات إلى نصوص مقروءة قبل إرسالها للواجهة (مثال: "تم تغيير حالة العقد إلى مدفوع"). المشغلون هم الأولوية، وليس المحاسبون فقط.

#### 4. حماية البيانات الشخصية للعملاء (Tenant PII Protection)

- **المشكلة:** عند تسجيل أحداث تخص المستأجرين (مثل إضافة حجز جديد)، قد يتسرب رقم الهوية، جواز السفر، أو بيانات البطاقة الائتمانية إلى حقل `metadata`.
- **القرار المعماري:** يجب تحديث مصفوفة مفاتيح الإخفاء (Redaction Keys) في خدمة التدقيق لتشمل مفاتيح مثل `['passportNumber', 'nationalId', 'creditCard']` لضمان الامتثال لقوانين خصوصية البيانات، وعدم تخزينها كنص صريح في سجلات التدقيق أبدًا.
